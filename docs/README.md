# docs/

コードの全体の地図と、何かを足すときの手順の入口は `code-map.md`。

## 置き方

- **機能ごとに 1 ファイル**。ファイル名は機能の名前にする（例: `combat.md`、`turn-phase.md`）。**連番は振らない。**
- 書くのは**いまの仕様**だけ。経緯や議論は PR の本文に書き、ここには残さない。
- **全 PR が書き足すファイルは作らない**（進捗の記録、変更履歴、目次など）。
  この README にも一覧は置かない。一覧が要るならディレクトリを見る。
- 仕様の正しさは**テストで固定する**。文書とテストが食い違ったら、テストが正で、文書を直す。

- **調整値は、検査がコードと突き合わせる**（`tests/docs/test_doc_values.gd`）。食い違ったら、コードが正で、文書を直す。
  文書に機械のための印は要らない。次のどれかの書き方にすれば、検査が拾う。
  - 「いま」「いまの値」の列を持つ表の行に、定数の名前（`` `NAME` `` か `` `Class.NAME` ``）を書く。「いま」の列の先頭の数を、その定数と比べる。
  - 文の中で、数のすぐあとの括弧の先頭に定数の名前を書く（`` 14 歩（`HUNT_RADIUS`） ``）。
  - 定数を名指ししない表（駒の種類の表のように、行が種類や役割のもの）は、`test_doc_values.gd` に表と行の読み方を 1 つ足す。
- **CPU どうしの対戦の実測（勝率、使用回数、倒された割合など）は `docs/cpu-ai.md` の「いまの集計」だけに置く。**
  実測は測った時点の値で、必ず古くなる。ほかの文書は、「なぜこの値にしたか」を数字を並べずに書き、比べた表と数字は PR の本文に残す。

機能を 1 つ入れる PR は、ふつう「その機能の文書 1 つ + コード + テスト」になる。
他の機能の文書には触らないので、並行する PR が衝突しない。

## コードの分け方

置き場所は `CLAUDE.md` の「検査」（ルールは `rules/`、画面は `game/`、道具は `tools/`、テストは `tests/`）。

- **1 ファイルが 600 行を超えてきたら、役割の切れ目で分ける。** 無理に細かく割らない。分けた先の名前を見て、何が入っているか分かること。
- 大きな場面・画面・道具は、もとのファイルと同じ名前のディレクトリ（`game/battle_screen/` など）に役割ごとのファイルを置き、
  土台（読み込み・調整値・状態の変数・小さな道具。`*_base.gd`）から順に `extends "res://…"` で継いで積み重ねる。
  **外から読むのは、いちばん後に継ぐもとのファイル**（`game/battle_screen.gd`、`rules/cpu_player.gd` の `CpuPlayer` など）で、継いだ定数・関数・static 関数もそこから読める。
- 継ぐ順と、どのファイルに何があるかは、もとのファイルの頭と、分けた先のファイルの頭（1〜2 行）に書く。関数を足すときは、そこを見て役割の合うファイルへ。
- **前のファイルは、後のファイルの関数を呼べない**（GDScript の解析が「見つからない」で落ちる）。呼ばれる側を前のファイルに置く。
  呼び合いがどうしても循環するなら、分け方を変える（土台へ下ろすか、同じファイルにまとめる）。
- コードのファイルを読んで見張るテストと道具は、下のディレクトリまで見る（`tests/game/test_text.gd`、`tests/game/test_sound.gd`、`tests/game/test_scene_flow.gd`）。
  定数を探すもの（`tests/docs/test_doc_values.gd`）は、継ぐ元のスクリプトの定数もたどる。
  別の版の CPU を読む道具（`tools/cpu_match.gd` の `load_rival`）は、その版の継ぐファイルも読む（`docs/cpu-ai.md` の「別の版と比べる」）。

## テスト

`tests/` の下に `test_*.gd` を置く。書き方は `tests/base_test.gd` の先頭に書いてある。
`tools/check.sh` が全部を実行する（CI も同じ）。テストだけなら次で動く。

    godot --headless --path . -s res://tools/run_tests.gd

- **画面の部品（Control）の大きさは、木に入れて 1 コマ待ってから測る**（`await settle(node)`。`tests/base_test.gd`）。
  木の外や、待たずに測ると、前に測った大きさが返り、文を替えても字の大きさを上書きしても変わらない（テストが素通りする）。
  中身を替えたら、測る前にもう一度 `settle` する。字の幅だけを見るなら、フォントの `get_string_size` で測ってよい（木は要らない）。
  大きさを確かめるテストを足したら、わざと壊して（文を長くする、字を大きくする）落ちることを 1 度見る。
- **ファイルを書くテストは、そのテストだけの置き場所に書く**（`user://test_<名前>_<乱数>` を `SaveStore.new()` に渡す、など）。
  `check.sh` はテストと自動の対戦をいくつものプロセスに分けて並べて回すので、決まった名前のファイルは取り合いになる。
  自動の対戦・スクリーンショット・通しの点検（`--autoplay`、`--shots`）は、セーブも設定も書かない（`game/app.gd`。覚えておくだけ）。
- **時刻で中身が変わるもの（保存の日時など）は、時計を止めるか進めて比べる**（`SaveSlots.now` を差し替える）。
  分の変わり目にだけ落ちる検査は、手元では通り、遅い CI でたまに落ちる。

## 検査の分け方

PR と push で回す検査は 90 秒をめやすにする（`CLAUDE.md`）。時間を切るためだけに分けない。時間の掛かるものは「長い検査」に分ける。

- `tools/check.sh <godot>`: PR ごとの検査（CI の `check`）。取り込みのあと、テストと自動の対戦を並べて回す。
  テストは 3 つのまとまりに分ける: 時間の掛かるファイル 2 組（`check.sh` の `TESTS_A` と `TESTS_B`）と、残り全部。
  控えた CPU どうしの 1 局（`tests/support/cpu_game.gd`）はプロセスごとに回るので、それを読むファイルは `TESTS_A` にまとめる。
  自動の対戦は、イベントを再生する場面 / 操作の決まりの場面 / 横長の画面での操作の決まりの場面（`check.sh` の `UI_WIDE`）の 3 つ。
  取り込みは、前半（素材の取り込み直しと、クラスの名前の控えなど `.godot/` の書き出し）が済んだ印がログに出たら止めて、先へ進む。
  後半はエディタの立ち上げ（メインのシーンを読む、エディタの設定を書く）だけで、メインのシーンが読めることは自動の対戦が確かめる。
  CI は、取り込んだ素材（`.godot/`）を控えて使い回す（`ci.yml`。素材の取り込みの設定が変わったら控え直す）。
- `tools/check.sh --full <godot>`: 長い検査。上に加えて、次も回す。CI の `full-check` が main に入ったあとに回す（手でも起動できる）。
  - 名前が `test_long_` で始まるテスト（同じ CPU どうしの対戦を何度も回して比べる、など）。
    テストだけなら `run_tests.gd -- --full`（`--long-only`、`--only=<語>`、`--except=<語>` で絞れる）。
  - 自動の対戦のほかのマップ（`-- --autoplay --full`）。
  - 通しの点検の長い道（`-- --autoplay --story-all` と `--versus-all`。`game/autoplay_sweeps.gd`）: すべての物語（本編の 2 つと番外）を、物語ごとに頭から `STORY_EPISODES` 話（いまは 15）まで画面の道で通す
    （会話・途中の台詞・わざと負けて負けの台詞）と、対戦モードの全部のマップ × 選べる決まりの入・切を数ターン。手で回すときは `tools/sweep.sh <godot> [story|versus|all]`。
  - 横長の画面（3440×1440）での、操作の決まりの場面の全部。PR ごとの検査は `UI_WIDE`（対戦の画面と対戦設定の場面）だけで、
    CPU の手番（`cpu`）・タイトル（`title`）・部隊編成（`decks`）・ストーリーの 1 話の通し（`story`）の横長は、長い検査だけで見る
    （どれも 1280×720 では PR ごとに回る）。
  - 部隊編成の持ち物の欄を、どちらの物語でも、全部の兵 × 全部の持ち物で見る（文が切れない、札が縮まない。`game/autoplay/story_checks.gd` の `_visit_item_rows`）。
    自動の対戦の操作の決まりの場面に `--full` を付けたときだけ回す。
  - スクリーンショットの場面のいくつかを、撮らずに作る（`-- --shots <場面,…> --dry-run`。場面は `check.sh` の `SHOTS_IN_FULL_A` と `_B`）。
    ルールや数値が変わって場面が作れなくなったことに、撮る人より先に気付くため。

長い検査は、時間の掛かるものをいくつかのまとまり（Godot のプロセス）に分けて並べて回す。いまのまとまり:
`test_long_` でないテスト 2 つ / 自動の対戦 3 つ / 全マップで CPU どうしが最後まで進むテストを軍の並びごとに 1 つずつ（2 つ）/
残りの `test_long_` 全部（`--except` で拾うので、足したテストが漏れない）/ 通しの点検の長い道 2 つ（話、対戦モード）/ スクリーンショットの場面を 2 つ。
手元（4 コア）で全体が 1 分半ほど、いちばん長いまとまりも 1 分半ほど。
まとまりごとの打ち切りは、PR ごとの検査で 120 秒、長い検査で 300 秒（`RUN_TIMEOUT` で変えられる）。
`check.sh` は終わりに、まとまりごとに掛かった秒数を出し、テストは 1 秒以上掛かったテストとファイルを出す。

マップや話が増えると伸びるもの:

- 全マップで CPU どうしが最後まで進むテスト。1 マップで 1 まとまりあたり 6〜8 秒伸びる（2 つのまとまりが並んで伸びる）。
- いちばん長いまとまりが 150 秒（打ち切りの半分）を超えたら、まとまりを分け直す（マップを半分ずつに分ける、など）か、
  毎回回すのを代表のマップに絞り、全部を回す入口を別に分ける。
  コア数（CI も手元も 4）より多く並べても全体は縮まないので、全体が 3 分を超えたら、絞るほうを選ぶ。

CPU どうしの 1 局を最後まで読むテストは、`tests/support/cpu_game.gd` が 1 回だけ回して控えた局を当て直して使う（CPU が考えるところが遅く、当て直すのは速い）。
同じ局で足りるなら、テストごとに対局を回さない。

長い検査へ回すのは「壊れても次の PR まで気付かなくてよい」もの。ルールのテストと、全種類のイベントを 1 回は再生する通しは PR ごとの検査に残す。
目安は、CI の `check` のジョブ全体が 50 秒ほど（手元の 4 コアで `check.sh` が 35 秒ほど。CI は手元の 1.3 倍ほど掛かり、ジョブの支度に 10 秒ほど足される）。
並べたまとまりで 4 コアがもう埋まっているので、まとまりを増やしても縮まない（テストのまとまりは、どれもテストのファイルを読むのに 3〜6 秒掛かり、
自動の対戦のまとまりは、立ち上げに 3 秒ほど掛かる）。測ると、いちばん長い `autoplay_ui` からストーリーの通し（`story`）を別のまとまりに分けると、
手元で全体が 3 秒ほど伸びた。場面をまとまりの間で入れ替えても縮まなかった。
超えてきたら、まず `check.sh` の終わりに出る秒数（まとまりごと、テストとファイルごと）を見て `TESTS_A` / `TESTS_B` の釣り合いを直し、
それでも長ければ、遅いものを測って速くする（同じことを確かめる小さい盤・少ない局に）か、長い検査へ回す（回したものは上の一覧に足す）。
