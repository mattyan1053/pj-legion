# 作業のセッションの手順

依頼文とこのスキルだけで動けるようにしてある。決まりの本体は `CLAUDE.md`。ここでは書き写さず、作業の順に並べる。

## 始めるとき

1. `CLAUDE.md`、`docs/README.md`、依頼文が挙げる Issue と文書を読む。ルールや数値を変える仕事なら Issue #47、見た目や操作なら Issue #46、ストーリーや構想なら Issue #49 も読む（本文とコメント）。移植のときの経緯と実測は、閉じた Issue #8 のコメントにある。
2. **着手の前に、開いている PR を見る。** 同じものを作っている PR があれば、作らずにメインへ知らせる。
3. いまの仕様の正は `docs/`。元の仕様（`mattyan1053/pj-region` の `openspec/specs/`、非公開）は、全体の仕組みと画面の遷移を確かめたいときだけ読む
   （コンテナに無ければ `add_repo`）。**元のコードは移植しない**（`CLAUDE.md` の「進め方」）。
4. 仕事の種類に合うスキルがあれば、それも読む（依頼文が名前で指すことが多い）。
   - `measure-balance`: 数値や CPU の調整、釣り合いを CPU どうしの実測で決める・確かめる。
   - `playtest-sweep`: 通しで触って不具合を探す。
   - `docs-audit`: 文書を、いまのコードとテストに照らして棚卸しする。
   - `add-asset`: 絵・モデル・音などの素材を入れる。
5. ほかの作業のセッションが同時に動いていることがある。**着手の前と PR を出す前に、main を取り込む。**

## 作るもの

- ルールは `rules/` に、ノードに依存しない形で書く。**機能の文書（`docs/`）+ コード + テスト**をそろえる（`docs/README.md`）。
- ほかの文書の記述が古くなったら直す。
- 画面の文は `game/text/` の表に置き（コードに直書きしない。`docs/text.md`）、`docs/wording.md` の言葉の決まりに従う。説明書の調子にしない。
- UI のテーマが入ったら、色と枠の飾りはテーマに任せ、色を直書きしない。
- ルールを変えたら、画面の側（`game/`）は**追従だけ**入れる。新しいイベントを再生でき、検査が通るところまで。
  見た目の新しい作りは、依頼に無ければ積まない。

## 仕様に無いことの決め方

- **質問で止まらない。** ゲーム性が良くなるほうを自分で選ぶ。元の挙動を保つことは重要ではない（Issue #8 のコメント）。
- 数値は 1 か所にまとめ、機能の文書に「いまの仕様」「調整値」として書く。調整値は検査がコードと突き合わせる形で書き、CPU の実測は `docs/cpu-ai.md` の「いまの集計」だけに置く（`docs/README.md`）。
- 人間の答えがどうしても要る点は、実装を止めずに仮で決めて進め、メインへ送る（`send_message`）。

## 範囲を守る

- 依頼に無い変更を足さない。
- 関係の無い直したい点を見つけたら、直さずに終わりの報告に入れる。
- **ワークフロー（`.github/workflows/`）と `CLAUDE.md` は触らない。** 変える必要があれば、変えずに報告する。
- **GitHub への書き込み（PR、コメント、マージ、Issue）は MCP の道具で行う。** `gh api` で書き込まない。

## 終わりの条件

- `tools/check.sh godot` が通る。PR と push で回る CI は 1 分以内に収める。
- 見た目やルールを大きく変えたときは、長い検査 `tools/check.sh --full godot` も手元で通す。
- ブランチを切って PR を開く。タイトルと本文は日本語、コミットは gitmoji + 英語の命令形。
- CI（`check` と `windows`）が緑で、PR を開いたときに付く Codex のレビューの指摘に対応し終えたら、merge commit で自分でマージする。
  **再レビューは頼まない。**
- 自分でマージしないものは `CLAUDE.md` の「Git」に従う。該当したら、マージせずに報告する。
- 依頼文が挙げる Issue（#47 / #46）の該当する項目にチェックを付ける（PR の番号を添える）。

### 人間に見た目を確かめてほしい PR

本文の先頭にそう書き、何を見てほしいかと、exe の入手先（CI の `windows` の成果物 `pj-legion-windows`）を示す。
返事は待たずにマージしてよい。

- **スクリーンショットを本文に貼る**（人間はスマホで見ることが多い）。`tools/screenshots.sh` で撮り、
  `tools/publish_screenshots.sh` で `screenshots` ブランチに置いて、出てきた Markdown を貼る（`docs/screenshots.md`）。
  変わった場面を選んで数枚。無い場面は `tools/screenshots.gd` に足す。前後を比べられるなら、main で撮ったものと並べる。
- **撮った絵を自分でも見て**、崩れ（文字の重なり、はみ出し、読めない色）が無いかを確かめる。
- コンテナの描画は Windows の実機と違う。最終の見え方は exe で確かめてもらう、と本文に書く。

## 終わりの報告

`send_message`（claude-code-remote）で、依頼してきたメインのセッション（依頼文に ID がある。`@parent` でも届く）へ短く送る。入れるもの:

- PR の番号（マージしたか、しなかったなら理由）
- 自分で決めた点と、その理由
- 見送ったもの
- ルールや土台に足りなかったもの
- 確かめられなかったこと（特に見た目と操作感）
