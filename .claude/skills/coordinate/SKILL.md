# メインのセッションの手順

このセッションは窓口。**コードは基本的に書かない**（書くと、作業のセッションと同じファイルを触って衝突する）。

## 始めるとき

1. `CLAUDE.md` と Issue #47、Issue #46 を読む。
2. 開いている PR と、動いている作業のセッションを確かめる。
3. 次にやることを人間に 1 つ提案する。Issue #47 と #46 の未決の点のうち、次の仕事に関わるものは先に人間に聞く。

## 仕事を渡すとき

- 作業のセッションは **1 機能ごとに新しく立てる**。使い回さない。
- 環境は `pj-legion`（Godot が `godot` として入っている）。環境の ID は一覧から引く。
- **モデルは、渡す仕事の難しさで選ぶ**（指定しないとメインのモデルを引き継ぐ）。迷ったら、足りる中でいちばん軽いものにする。
  - 手順が決まっていて、判断がほとんど要らない仕事（用意された道具を回して結果を貼る、文書の決まった書き換え、名前の付け替えなど）は Sonnet（`claude-sonnet-5-5`）。さらに単純なら Haiku（`claude-haiku-5-5`）。
  - **ふつうの仕事は Opus（`claude-opus-5-5`）。** 仕様に無い点を決めることが含まれていても、結果を道具で確かめられる仕事（テスト、CPU どうしの対戦の集計、新旧の CPU の比べ、スクリーンショット）は Opus に出す。数値の調整、CPU の改良、仕様のある機能の追加、土台の整理はここ。
  - **Fable（`claude-fable-5-2`）は、人間の利用枠が限られているので、絞って使う。** 出すのは、何も無いところから中身を設計し、しかも良し悪しを道具で確かめにくい仕事だけ（例: 操作や画面の作りの最初の形、仕様に中身の無いものを一から考える）。1 つの話題で続けて Fable を使わない（最初の形を Fable が作ったら、直しや続きは Opus）。
  - 迷うときは、Fable には「設計を短い文書か Issue にまとめるところまで」を頼み、作るのは Opus に渡す形を考える。
  - 軽いモデルに渡した仕事が手順どおりに終わらなかったら（検査が通らない、報告が来ない）、同じ依頼を 1 段上のモデルで立て直す。
- 同時に動かすのは、ルール（`rules/`）を変える仕事 1 本と、それと独立な作業（見た目など）1 本まで。
- **仕事の分け方とまとめ方は、メインが判断する。** 渡す前に、1 つのセッション・1 つの PR にまとめるか、分けるかを決める。
  - 意図の違う変更は、別のセッション・別の PR に分ける。進行中の作業のセッションに、関係の無い変更を後から足さない。
  - 同じファイルを触る、同じ判断の続きである、といった近い変更はまとめてよい。
  - 後から足したいことが出たら、いまの仕事と同じ意図かどうかで決める。
- 依頼文は「`work` のスキル（`.claude/skills/work/SKILL.md`）に従う」と書き、そのあとに**その仕事に固有のことだけ**を入れる。
  共通の手順（読むもの、作るものの形、終わりの条件、報告）はスキルにあるので書き写さない。入れるもの:
  - 何を作るか（Issue #47 / #46 のどの項目か。仕様があれば `pj-region` のどの仕様か）
  - 人間が決めたこと（未決の点への答え）
  - 入れないもの（触らないファイル、見送る範囲）
  - PR を自分でマージしない場合（その仕事が `CLAUDE.md` の「Git」に当たるとき）
  - メインのセッションの ID（報告の宛先）
- 作業のセッションが人間に聞きたいことは、メインが受けて人間に聞き、答えを返す。

## 人間の話したことを残す

ゲーム作りはその場のアイデアが大事。口頭の話を、きちんとためる。その場の思い付きなので、過去の仕様や決定と食い違うこともある。それは、そのときに個別に考える。

- 人間が話したアイデア・感想・決定は、**その返事のうちに**残す。あとでまとめて、にしない。セッションの記憶に置かない。
- **種類を付けて残す。**
  - **感想**（遊んで気付いたこと。直すもの）→ Issue #46。
  - **決定**（こうする、と人間が決めたこと）→ 関わる Issue（ルールと数値は #47、見た目と操作は #46）。仕様になるものは、それを入れる PR が `docs/` に書く。
  - **案**（やるかどうか、まだ決めていないもの）→ 関わる Issue に「案」と分かる形で。
  - **構想**（だいぶ先の話。いまは作らないもの）→ Issue #49。
  - どれにも合わない話題が続くなら、受け皿の Issue を 1 つ足す。Issue を話題ごとに細かく増やさない。
- **残す前に、いまの仕様や過去の決定と食い違わないかを見る**（関わる `docs/` の文書と Issue）。
  食い違っていたら、**黙ってどちらかに合わせず、その場で人間に言う**（何と何が食い違うか）。
  人間がその場で決めたら決定として残す。決めなければ「未決（食い違いあり）」として残す。
- 残したら、どこに残したかを人間に 1 行で伝える。
- 案や構想が**決定に変わったら**、元の項目にそう書き足す（消さない）。
- Issue のコメントが増えて読みにくくなったら、「進め方の見直し」のときに、本文を「いまのまとめ」に書き直す（コメントは経緯として残る）。

## 待つとき

作業のセッションは終わりに報告を送ってくる。**それを待つのを基本にする。**
自分から見に行く（セッションの状態と、PR の状態）のは、報告が来ないときの備えとして、間隔を長めに取る（60 分ほど。集計を回す長い仕事はもっと長くてよい）。
見に行くたびにメインの利用枠を使うので、短い間隔で回さない。何も変わっていなければ人間には言わない。

## 戻ってきたとき

- PR の本文、差分、CI を見る。仕様（`pj-region` の `openspec/specs/`）と食い違っていないか、
  `docs/` の文書とテストが付いているかを確かめる。
- Issue #47 / #46 の該当する項目にチェックを付ける。決まったことが増えていれば、`CLAUDE.md`、Issue、`docs/` のどれかに書く。
- **確かめ終えた作業のセッションは、アーカイブする**（残すと一覧に増え続ける）。
- 人間には、何が入ったか、見てほしいものがあるか、次に何をやるかを短く伝える。

## 進め方の見直し

- まとまった仕事（Issue #47 や #46 の 1 つの節、または PR 5 本ほど）が終わるごとに見直す。作業のセッションの報告に繰り返し出た手間
  （同じ説明の書き写し、同じ種類の抜け、手で確かめていること）を拾う。
- Claude の仕組み（スキル、エージェントの定義、フック、設定、定期の実行、PR の監視など）で減らせるなら、
  取り込む変更を 1 つ人間に提案し、別の PR で入れる。
- 見直しのたびに、文書の棚卸しを回す（前の棚卸しのあとに変わった機能の文書を、コードとテストに照らす）。
- 仕組みは変わるのが速い。記憶で決めず、いまの文書を確かめてから提案する。
- 権限や安全に関わる変更（`.claude/settings.json` など）は自分でマージしない（`CLAUDE.md` の「Git」）。
